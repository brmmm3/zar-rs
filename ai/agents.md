# ZAR implementation notes

## Workspace

- Rust 2024 workspace with `zarlib` (format/library), `zarc` (CLI), `zarg` (GUI), `pyzarlib`, `czarlib`, `cxxzarlib` (wrappers), and `zcopy` (network copy).
- Format plan: [plan.md](./plan.md).

## Implemented

- Container magic (`ZAR0`) with a 12-byte container header (`ZAR0` magic + 8-byte little-endian `first_header_offset`). Each commit uses a 22-byte little-endian `CommitHeader` (`ZCMT` magic + version + flags + commit_id + data_section_size + header_frame_size) with xxhash64 integrity checks and checked size arithmetic. The new format stores data blocks first, then the header frame at the end, enabling direct streaming to the final file without temporary staging.
- Header and data-block frame encoding/decoding with bounded payload reads, Zstandard compression/decompression, and xxhash64 payload checksums. Block encryption AAD uses `CommitHeader::identity_bytes()` (magic + version + flags + commit_id, 10 bytes) to avoid a chicken-and-egg dependency on `data_section_size`.
- Stable encryption-descriptor wire encoding, parameter validation, optional TLV handling, and scope metadata. Content encryption supports AES-256-GCM and ChaCha20-Poly1305; password-based DEK wrapping uses bounded Argon2id parameters. Encrypted archive creation generates the DEK before scanning and encrypts data blocks inline via `EncryptionContext` in `ScanContext`.
- Commit-body framing validation for descriptors, frame integrity, block-index uniqueness, encryption scope consistency, duplicate nonces, frame size limits, and block-count limits. Readable logical headers are decompressed and decoded during validation, then each new file operation is checked against blocks in that commit; password-aware CLI flows authenticate/decrypt encrypted headers and data blocks before validation. Data-only encryption descriptors permit header compression/decompression.
- Canonical archive-relative UTF-8 path validation using `ArchivePath`: slash-separated paths only, rejecting absolute/drive-prefixed paths, empty/dot/parent components, NUL, and backslashes. Comparison is exact (no case folding or Unicode normalization).
- In-memory logical TOC model with file and directory entries, ordered put/remove operations, recursive directory removal, path-kind conflict detection, and atomic per-commit application. The `apply_commit_with_available_blocks` API validates each newly added file's references against the current commit's validated block indices while preserving existing references to blocks in prior commits. `ValidatedCommit` exposes the block-index set collected during frame validation.
- Canonical project logical-header v0 encoding/decoding for ordered TOC operations, using the fixed `ZHDR` magic, little-endian version/count/length/size/index fields, explicit record tags, bounded limits, and canonical `ArchivePath` validation. The byte layout is specified in `plan.md` and pinned by a golden encode/decode compatibility vector. It rejects unknown versions/tags, invalid UTF-8/path data, truncation (including implausible declared block-reference counts before allocation), and trailing bytes.
- CLI `check` validates commit bodies and frame integrity, decompresses and verifies every unencrypted data block, reconstructs readable TOC changes across commits, checks per-commit block references, and verifies decoded file sizes. With `--password`, it authenticates/decrypts encrypted headers and data blocks; without credentials, encrypted portions remain explicitly unverified. `info` lists commit prefix sizes and IDs. `list` validates and applies logical headers in commit order, checks each commit's new file references against that commit's block indices, and prints the final TOC; header-encrypted commits can be listed when unlocked with `--password`.
- CLI `extract` processes commits in order and associates block indices only with their owning commit. It validates each block during planning but retains only its archive offset and decoded size; selected blocks are decoded again and streamed directly to output files, avoiding whole-archive and whole-file content buffers. It supports `--to DIR` and `--dry-run`, verifies reconstructed file sizes, and rejects encrypted commits unless unlocked with `--password`. Unix extraction uses directory file descriptors and `openat`/`mkdirat` with `O_NOFOLLOW` for each destination component, and exclusive file creation for `error`/`skip` policies; overwrite opens the leaf without following symlinks and verifies the opened object is a regular file. This prevents path-component symlink swaps and overwrite races on Unix. The non-Unix fallback uses standard path-based directory and file operations and therefore does not provide equivalent race resistance.
- CLI extraction tests cover nested paths, dry-run non-mutation, size mismatch rejection, encrypted-data rejection and password unlock, block-index reuse across commits, and Unix no-follow file creation that preserves symlink targets and files appearing concurrently under `error`/`skip` policies.
- CLI `create` builds a one-commit archive (unencrypted or encrypted) from files/directories. It sorts directory entries, skips symlinks and special files with warnings, requires UTF-8 names, rejects duplicate archive paths and existing output files unless `--overwrite` is selected, and validates the staged archive before publishing it. Block size defaults to 8 MiB and Zstandard compression level defaults to 3; `--block-size` accepts byte counts, `K`/`M` suffixes, or `auto` (which selects a 1–8 MiB block based on 50% of currently available memory and a bounded per-worker estimate), while `--compression-level` accepts -7 through 22. Manually selected block sizes are limited to 64 KiB–32 MiB. Publication uses a hard link so a concurrently created destination is not overwritten, and temporary files are cleaned up on failure. Inputs are mapped to canonical archive-relative paths; outside-working-directory absolute inputs use their basename. Empty files are supported. Include/exclude file and folder patterns and filter-list files are available for selecting inputs.
- CLI `add <archive> <paths...>` appends a commit to an existing archive, unencrypted by default or encrypted when `--password` is supplied. It accepts the same `--block-size` and `--compression-level` settings (including memory-budget-based `auto` sizing), assigning local block indices and validating the combined archive before publication. For encrypted history, provide credentials for encrypted commits that must be validated. It atomically replaces the original via a staged file in the archive's parent directory; on failure, the original archive is preserved and staged files are removed. Existing file paths are replaced according to ordered TOC semantics. Appending is unsupported when the effective TOC cannot be authenticated/read with the supplied credentials.
- CLI `join <archive> --from ID --through ID` compacts an inclusive contiguous range in physical commit order into one replacement commit at that range's original position. It accepts configurable `--block-size` and `--compression-level` options (the same defaults and validation as create/add, including automatic memory-budget sizing). The join preserves the final TOC state after the selected commits, materializes referenced file data into new local block indices, and retains commits outside the range unchanged. It rejects malformed, missing, or ambiguous IDs, reversed ranges, unreadable/encrypted state, and archives where a later encrypted header prevents final TOC validation. The archive is staged and validated before atomic replacement, preserving the source on failure. Encrypted stateful joins are unsupported; password-aware reading and extraction are implemented, but join does not decrypt and re-encrypt commits.
- CLI `remove <archive> <paths...>` appends a logical tombstone commit for each requested existing archive path. Removing a directory recursively removes its descendants from the effective TOC; removal does not rewrite old commits or reclaim their data. It builds and validates a staged combined archive before replacing the original, and preserves the original archive if validation or staging fails. Removing from archives with header-encrypted commits is unsupported because the effective TOC cannot be read.
- CLI tests cover nested file/directory round-trip extraction, empty files, archive validation, refusal to overwrite an existing output, appending a new file while preserving existing contents, replacing an existing file, file and recursive-directory removal, range joins including replacement/tombstone effects and a later suffix commit, and failure cleanup/original-archive preservation.
- Listing uses a TOC-only load path that validates commit frames and logical-header block references without decoding data blocks. It can list data-encrypted commits when their headers are readable; password-aware listing unlocks header-encrypted commits. `--through` stops applying logical state after the selected commit while still validating subsequent commit framing/IDs.
- Extraction supports collision policies (`error`, `first`, `latest`, `rename`, and interactive `ask`) and existing-file policies (`error`, `skip`, `overwrite`, and interactive `ask`). Case-folded archive path collisions are resolved according to TOC lexical ordering; rename candidates are reserved to avoid planned-path collisions. Tests cover first/latest/rename behavior and existing-file skip/overwrite.
- Extraction `--through` tests now cover malformed, missing, and duplicate IDs, plus successful extraction through an earlier readable commit when a later commit is data-encrypted. Dry-run plan formatting is independently tested for the final TOC and planned directory/file actions. Non-interactive `ask` policies are tested to fail early, and existing-file `error` is verified not to overwrite the destination.

## Current limitations / next work

- Logical-header v0 serialization encodes TOC operations and file block indices using the canonical project wire layout specified in `plan.md`; compatibility is pinned by a complete fixed-byte golden vector.
- `zarc check` verifies framing, stored checksums, decompression of unencrypted data blocks, readable cumulative TOC updates, block references, and decoded file sizes. It cannot validate encrypted block contents or logical state hidden by encrypted headers; it reports these limitations while continuing checks that remain possible.
- Archive creation supports one commit (unencrypted or encrypted); `zarc add` appends unencrypted commits, `zarc remove` appends TOC tombstones, and `zarc join` compacts a selected readable contiguous range. Creation, append, and join accept configurable block size and compression level. Logical-header v0 uses the canonical project encoding described in `plan.md`.
- The library provides AES-256-GCM and ChaCha20-Poly1305 content encryption, plus Argon2id password-based DEK wrapping. `zarc create --password` prompts without echo and creates encrypted archives with inline data block encryption (no staging file needed). Password-aware `check`, `list`, and `extract` prompt without echo, authenticate encrypted content, and keep extraction streamed; wrong or missing credentials fail before extraction writes files. DEKs and transient key material use zeroizing buffers, and the AEAD backends enable their zeroize features. Encryption dependencies are `aes-gcm 0.11.1`, `argon2 0.6.0`, `chacha20poly1305 0.11.0`, and `getrandom 0.4.3`; nonce construction uses the current `TryFrom` API. `remove` and `join` still reject encrypted archives whose stateful TOCs cannot be read and rewritten. Encrypted `add` validates the existing encrypted history with supplied credentials before staging or mutation.
- The logical-header v0 encoding is canonical for this project; any future wire-format revisions require an explicit versioned compatibility decision.

## Archive validation and recovery

`zarc check <ARCHIVE> --recover` opts into scanning past damaged framing for a later commit with a valid prefix and body. It reports recovered gaps and returns warning exit code 1; it does not modify or repair the archive. Any gap resets accumulated logical TOC state, so the recovered suffix is validated independently. Without `--recover`, archive checking remains strict.

It supports browsing and virtualized listings, create/add/remove/join/check/info/list/extract flows, progress and warnings, collision/existing-file policies, metadata and special-file options, and embedded KDE4 Crystal Diamond icons with license/attribution documentation.
- Added `pyzarlib`, a PyO3 wrapper over the Rust library, plus pytest coverage, a Python `zarc` example CLI, and examples corresponding to the Rust CLI operations. The Python API includes create/add/remove/join/check/info/list/extract and streaming/in-memory extraction with per-file size limits and offsets.
- Declared Python 3.9–3.15 support and configured CI for CPython 3.9 through 3.15 and free-threaded CPython 3.14t/3.15t. PyO3 declares that the extension does not require the GIL; concurrent-call and free-threaded import tests cover that property. Local validation today used CPython 3.13.9; the CI matrix is the repeatable coverage for the other interpreters.
- Added `czarlib`, a C ABI wrapper with a UTF-8 JSON request/response dispatcher, public header, C example, and C integration tests. It exposes the same archive operation surface as the Python package, including extraction to memory.
- Extended password encryption consistently across Rust, CLI, Python, and C. Commits can encrypt data only, header only, or both; each commit records its AEAD and encryption scope. Read APIs accept a per-commit password mapping, with explicit commit credentials overriding one default fallback. CLI `--password-for COMMIT_ID` prompts for commit-specific credentials. `info` includes header/data encryption status and algorithm. Canonical displayed commit IDs are eight hexadecimal digits in counter order. Existing encrypted commits can be validated for encrypted append when matching credentials are supplied; `remove` and stateful `join` remain unsupported for encrypted TOCs.
- Added a Linux archive benchmark runner at [`../scripts/benchmark_archivers.py`](../scripts/benchmark_archivers.py). It obtains and safely validates `linux-4.0.1.tar.gz`, refreshes an inconsistent extraction, compares plain/encrypted zarlib, ZIP, 7z, and tar.gz, verifies extracted regular-file paths and sizes, and cleans `testresults/` after each run. Since tar.gz has no encryption, its encrypted comparison wraps tar.gz in OpenSSL CMS AES-256-GCM. Generated results and SVG charts are in [`../doc/benchmark-report-linux.md`](../doc/benchmark-report-linux.md) and [`../doc/benchmark-charts-linux.svg`](../doc/benchmark-charts-linux.svg). The report documents the different encryption modes and link-handling caveats; measurements are single runs, not statistical averages.
- Updated package READMEs and developer documentation with build/test instructions, operation examples, encryption/password behavior, Python compatibility, and C API usage.

- Added `zcopy`, a binary workspace crate that copies file trees between machines. The client pushes to a server (`-s <FOLDER>`, created if missing; `-c <HOST[:PORT]>`). The server scans its folder with `scandir` (3.0, the version `zarlib` already uses, rather than the older `scandir_rs`), caches the metadata, and sends it zstd-compressed on connect. The client sends only files that are missing or have a newer mtime, plus empty directories, in batches built with the `zarlib` create pipeline and extracted by the server with the extract pipeline; the server restores mtimes. Options: password, AEAD, compression level, allow list of names/IPs, port, bind address, batch size, all also loadable from `zcopy.json` (CLI wins). With a password the control channel is AES-256-GCM (Argon2id key, per-connection salt, direction/counter nonces) and archives are encrypted by `zarlib`. Validation: 6 unit/integration tests (sync, incremental resend, restart rescan, password, wrong password, allow list), clippy clean, and a manual release run with a config file where a repeat run sent nothing. See [`../zcopy/README.md`](../zcopy/README.md).
- `zcopy` follow-ups: server rejects client paths that escape the root or traverse symlinks (`resolve_inside`); the client shows an `indicatif` progress bar like `zarc` (`--no-progress` to hide); `--metadata`/`"metadata"` transfers permissions and ownership and is applied only if the server enables it too; the server accepts concurrent clients and, when others are connected, the new client is warned and asked to continue (`--yes` skips the question, non-terminal input cancels). A new `Proceed` message follows the manifest. 7 tests pass (concurrency warning and metadata gating included) and clippy is clean. The progress bar rendering was not inspected visually.
