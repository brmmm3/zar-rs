# ZAR implementation notes

## Workspace

- Rust 2024 workspace with `zarlib` (format/library) and `zarc` (CLI).
- Format plan: [plan.md](./plan.md).

## Implemented

- Container magic (`ZAR0`) and 56-byte little-endian commit prefixes (`ZCMT`) with xxhash64 integrity checks and checked size arithmetic.
- Header and data-block frame encoding/decoding with bounded payload reads, Zstandard compression/decompression, and xxhash64 payload checksums.
- Stable encryption-descriptor wire encoding, parameter validation, optional TLV handling, and scope metadata. Cryptographic encryption/decryption and key derivation are not implemented.
- Commit-body framing validation for descriptors, frame integrity, block-index uniqueness, encryption scope consistency, duplicate nonces, frame size limits, and block-count limits. Unencrypted logical headers are decompressed and decoded during validation, then each new file operation is checked against blocks in that commit; encrypted headers remain opaque because decryption is unsupported. Data-only encryption descriptors still permit header compression/decompression, while header-encrypted descriptors are rejected by plaintext header operations.
- Canonical archive-relative UTF-8 path validation using `ArchivePath`: slash-separated paths only, rejecting absolute/drive-prefixed paths, empty/dot/parent components, NUL, and backslashes. Comparison is exact (no case folding or Unicode normalization).
- In-memory logical TOC model with file and directory entries, ordered put/remove operations, recursive directory removal, path-kind conflict detection, and atomic per-commit application. The `apply_commit_with_available_blocks` API validates each newly added file's references against the current commit's validated block indices while preserving existing references to blocks in prior commits. `ValidatedCommit` exposes the block-index set collected during frame validation.
- Provisional logical-header v0 encoding/decoding for ordered TOC operations, using explicit record tags, little-endian integer fields, bounded allocation/size limits, and canonical `ArchivePath` validation. It rejects unknown versions/tags, invalid UTF-8/path data, truncated records (including implausible declared block-reference counts before allocation), and trailing bytes. This layout is provisional and must be reconciled with the authoritative format specification before interoperability is claimed.
- CLI `check` validates commit bodies and frame integrity; `info` lists commit prefix sizes and IDs. `list` validates and applies readable logical headers in commit order, checks each commit's new file references against that commit's block indices, and prints the final TOC.
- CLI `extract` materializes readable, unencrypted file contents by processing commits in order and associating block indices only with their owning commit. It supports `--to DIR` and `--dry-run`, verifies reconstructed file sizes, and rejects header- or data-encrypted commits. Before writing, it checks destination targets for symlinks and incompatible existing file/directory types.
- CLI extraction tests cover nested paths, dry-run non-mutation, size mismatch rejection, encrypted-data rejection, and block-index reuse across commits.
- CLI `create` builds a one-commit, unencrypted archive from files/directories. It sorts directory entries, skips symlinks and special files with warnings, requires UTF-8 names, rejects duplicate archive paths and existing output files, writes data in 8 MiB compressed blocks (Zstandard level 3), validates the staged archive, and only then hard-links it to the requested output so a concurrently created destination is not overwritten. Temporary files are cleaned up on failure. Inputs are mapped to canonical archive-relative paths; outside-working-directory absolute inputs use their basename. Empty files are supported.
- CLI `add <archive> <paths...>` appends a new unencrypted commit to an existing readable archive. It assigns block indices local to the new commit, validates the combined archive before publication, and atomically replaces the original via a staged file in the archive's parent directory. On failure, the original archive is preserved and staged files are removed. Existing file paths are replaced according to ordered TOC semantics. Appending is unsupported for archives whose accumulated TOC requires decrypting a header-encrypted commit.
- CLI `join <archive> --from ID --through ID` compacts an inclusive contiguous range in physical commit order into one replacement commit at that range's original position. The join preserves the final TOC state after the selected commits, materializes referenced file data into new local block indices, and retains commits outside the range unchanged. It rejects malformed, missing, or ambiguous IDs, reversed ranges, unreadable/encrypted state, and archives where a later encrypted header prevents final TOC validation. The archive is staged and validated before atomic replacement, preserving the source on failure. Encryption/decryption is not implemented, so encrypted stateful joins are explicitly unsupported.
- CLI `remove <archive> <paths...>` appends a logical tombstone commit for each requested existing archive path. Removing a directory recursively removes its descendants from the effective TOC; removal does not rewrite old commits or reclaim their data. It builds and validates a staged combined archive before replacing the original, and preserves the original archive if validation or staging fails. Removing from archives with header-encrypted commits is unsupported because the effective TOC cannot be read.
- CLI tests cover nested file/directory round-trip extraction, empty files, archive validation, refusal to overwrite an existing output, appending a new file while preserving existing contents, replacing an existing file, file and recursive-directory removal, range joins including replacement/tombstone effects and a later suffix commit, and failure cleanup/original-archive preservation.

## Current limitations / next work

- Logical-header v0 serialization currently encodes TOC operations and file block indices, but format-wide canonical interoperability is not established until the provisional wire layout is verified against the authoritative specification.
- `zarc check` verifies framing and stored checksums, not decryption, decompression of all data frames, or logical archive consistency.
- Archive creation supports one unencrypted commit; `zarc add` appends unencrypted commits, `zarc remove` appends TOC tombstones, and `zarc join` compacts a selected readable contiguous range. Options for block size or compression level are not implemented. The provisional logical-header encoding is not yet established as interoperable.
- Encryption descriptors are parsed and validated, but encryption and decryption are unsupported.
- Extraction is memory-backed and bounded to 32 MiB per decoded block by default. Destination symlink checks are not atomic with file creation, so concurrent filesystem changes could create a time-of-check/time-of-use race.
- Verify all provisional wire-format choices against the authoritative format specification before treating them as finalized.

## Validation

Latest validation after implementing `zarc join`: `cargo fmt --all`, `cargo test --workspace` (15 CLI tests and 37 library tests), and `cargo clippy --workspace --all-targets -- -D warnings`. Join tests cover compaction with tombstones and replacements, preservation of commits before and after the selected range, invalid/reversed IDs and preservation of the original archive on errors. CLI extraction tests cover nested paths, dry-run non-mutation, size mismatch rejection, encrypted-data rejection, and block-index reuse across commits. Creation tests cover nested files/directories, zero-length files, full validation, round-trip extraction, and refusing to overwrite an existing archive. Add tests cover appending a commit, preserving earlier contents, file replacement, full validation and extraction, and failure cleanup with the original archive preserved. Remove tests cover file removal, recursive directory removal, framing validation, and preservation of the original archive on a missing-path error. Creation uses exclusive temporary files and a final hard-link operation to avoid overwriting a destination created concurrently. Append and remove stage the new commit and full archive in the target directory, validate all commit frames and the resulting logical TOC before rename, and clean temporary files on failure. Commit validation checks new file references against blocks in the current commit; TOC application preserves entries from earlier commits. CLI extraction decodes each commit's unencrypted blocks and materializes file data before writing the final TOC.
